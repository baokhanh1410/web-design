## Part 1 — SQL Warm-up

### Question 1
- `INSERT INTO team (name, headquarters) VALUES ('Avengers', 'Los Angeles');`
  - Blocked by: `UNIQUE` constraint on `team.name`.
  - Reason: A record with `name = 'Avengers'` already exists.
- `INSERT INTO hero (name, team_id) VALUES ('Ghost', 99);`
  - Blocked by: `FOREIGN KEY` constraint on `hero.team_id`.
  - Reason: `team_id = 99` does not reference any existing `id` in the `team` table.
- `INSERT INTO hero (age) VALUES (30);`
  - Blocked by: `NOT NULL` constraint on `hero.name`.
  - Reason: The column `name` is declared `NOT NULL` but no value was provided.
- `DELETE FROM team WHERE id = 1;`
  - Blocked by: `FOREIGN KEY` constraint.
  - Reason: Rows in the `hero` table still reference `team.id = 1`, violating referential integrity.

### Question 2
The foreign key is on `hero` because the relationship is one-to-many (one team has many heroes). Placing `team_id` on each hero record allows multiple heroes to point to the same team. If the foreign key were placed on `team`, a team could only reference a single hero unless using non-relational arrays.

## Part 5 — CRUD Endpoints for Heroes

### Question 10
- Omitting `session.commit()`: The new row is not persisted in the database (`SELECT * FROM hero;` shows no new row). Calling `session.refresh()` fails or returns an unpersisted object without an ID because the transaction was not committed.
- `session.add()`: Places the object into the pending set of the current database session transaction without committing to disk.
- `session.refresh()`: Re-queries the database to load attributes generated by the database (such as auto-incrementing `id` or default column values) into the Python object.

### Question 11
SQL printed by `echo=True`:
```sql
UPDATE hero SET age=%(age)s::INTEGER WHERE hero.id = %(hero_id)s::INTEGER
```
It updates only `age` because `model_dump(exclude_unset=True)` only includes fields sent in the request payload, leaving other columns untouched during `sqlmodel_update`.

### Question 12

Since `HeroPublic` does not declare `secret_name`, FastAPI filters it out during response serialization.

## Part 6 — Teams, Filtering, Pagination and Errors

### Question 13
```sql
SELECT hero.name, hero.age, hero.team_id, hero.power, hero.id, hero.secret_name 
FROM hero 
WHERE hero.age >= %(age_1)s::INTEGER AND hero.team_id = %(team_id_1)s::INTEGER ORDER BY hero.id 
LIMIT %(param_1)s::INTEGER OFFSET %(param_2)s::INTEGER
```
- Where the values appear: The values 18 and 1 appear in the parameters dictionary (`{'age_1': 18, 'team_id_1': 1}`), not in the SQL statement string itself.
- SQL injection safety: The query engine uses parameterized queries (prepared statements), so user input is treated strictly as literal data values and cannot alter SQL command structure.

### Question 14
Filtering at the database level uses indexes, query planning, and minimizes data transferred over the network. Filtering in Python fetches the entire table into application memory first, causing severe performance degradation and high memory usage as data grows.

## Part 9 — Migrations with Alembic

### Question 17
- `\d hero` shows no `power` column.
- Calling `GET /heroes` returns heroes with `power: null` (or fails if required) because `create_all()` does not perform schema alterations on existing tables.
- "Drop all tables and run create_all again" is unacceptable in production because dropping tables destroys all existing user and business data.

### Question 18
```python
def upgrade() -> None:
    op.add_column('hero', sa.Column('power', sqlmodel.sql.sqltypes.AutoString(), nullable=True))

def downgrade() -> None:
    op.drop_column('hero', 'power')
```
- `upgrade()`: Adds the `power` column to the `hero` table in the database.
- `downgrade()`: Removes the `power` column from the `hero` table to revert the schema change.

### Question 19
- Alembic tracks the current revision in a dedicated table named `alembic_version` in the database.
- `migrations/` should be committed to Git so that database schema changes are versioned, shared across developers, and applied deterministically in all environments.

### Question 20
- Autogenerate generates:
  ```python
  op.drop_column('hero', 'secret_name')
  op.add_column('hero', sa.Column('alias', sqlmodel.sql.sqltypes.AutoString(), nullable=False))
  ```
- Danger: Dropping `secret_name` permanently deletes all existing data in that column.
- Fix: Replace the drop/add calls with a column rename operation:
  ```python
  op.alter_column('hero', 'secret_name', new_column_name='alias')
  ```

## Review Questions

1. **What is a primary key for?**
   Uniquely identifies each row/record in a database table.
2. **What is the main benefit of an ORM?**
   Maps database tables to programming language classes and objects, enabling type safety and eliminating repetitive raw SQL queries.
3. **What does table=True change about a SQLModel class?**
   Instructs SQLModel to configure the class as an actual SQLAlchemy database table mapped to a database table.
4. **After session.add(...), what actually saves the data to the database?**
   `session.commit()`
5. **What does session.exec(select(Model)).all() return?**
   A list of instances of `Model` matching the query.
6. **What is Alembic for?**
   Tracking, managing, and applying database schema migrations over time without losing data.
7. **You add a field to a model and restart the app. Why is there no new column?**
   `create_all()` only creates missing tables; it never alters existing table structures.
8. **In a one-to-many Team–Hero relationship, where does the foreign key go?**
   On the "many" side of the relationship (`hero.team_id`).
